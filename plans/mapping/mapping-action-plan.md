## 0. Conventions that apply to every pass (read first)

| Topic | Rule |
|---|---|
| Addresses vs locations | Blazer is **LoROM**, 1 MiB = 32 banks of 32 KB. Every JSON key and every `start`/`end` is a decimal **file offset**. SNES bank = `offset >> 15`; SNES address = `$8000 + (offset & $7FFF)`. Example: offset 22012 (`0x55FC`) = `$00:D5FC`. The label suffix is the *file offset in hex* (`native_mode_brk_0055FC` = offset `0x55FC`), not the SNES address. Never convert by eye; use `npm run extract:lt` (`; {n}` tag = decimal file offset). |
| Two different "bank" numbers | `?BANK nn` in asm = SNES bank (`offset >> 15`). Notes/names storage banks (`notes/*/bankNN.json`, `us/names/bankNN.json`) = `floor(offset / 65536)`, i.e. 16 files `bank00..bank0F`. Do not mix them. |
| Rebuilt ROM | The rebuilt ROM has different data locations. Use `rebuilt/layout.json` for rebuilt locations. **Never compare original and rebuilt ROM bytes or locations** (workspace rule). Gates below only compare rebuilt vs rebuilt or check tool output. |
| Notes, comments, names | Only `npm run merge -- <spec> [--dry-run]` and `npm run names -- <spec> [--dry-run]`. No throwaway scripts. Name spec rows take `address` (the `; {n}` number) and `old` from `extract:lt` output, never from `blocks.json`. Specs go in `plans/extracted-audit/{edits,renames}/` (create it, same layout as IOG). |
| Assembler | `$&` = 2-byte same-bank, `$@` = 3-byte long. Bare `LSR`/`ASL`/`INC`/`DEC`/`ROL`/`ROR`. Label offset arithmetic is hexadecimal. |
| Git | The agent never commits. Each pass ends with a suggested commit message. |
| Gate command set | `npm run extract:lt` → `npm run rebuild` → `npm run names -- --check` → (after Pass 4) `npm run merge -- <spec> --dry-run`. A pass is done when all four succeed with no new warnings. |

## 8a. Pass 1 finding: rebuilt ROM capacity

- Layout content after Pass 1 is 1,055,033 bytes (was 1,048,204): +6,829 = the 6,746-byte graphic tail, the 33rd SFX (83 bytes) and the palette byte. The rebuilt ROM is still 1,081,344 bytes (33 pages), now with 6,692 bytes in the 33rd page.
- Root cause is not the new data. `gaia-core` expands every `Palette` to `0x200` bytes on extraction (`src/types/files.ts`, "compatible with yy-chr") and the rebuild writes the full 512 bytes back. In Blazer 83 palette files occupy 42,496 bytes in the rebuilt ROM but only 14,240 bytes of real data (`end - start` in `files.json`, which matches the asset-list palette size byte × 2): **28,256 bytes of padding**. Without that padding the content is about 1,026,777 bytes, 21,799 under 1 MiB.
- Options: (a) trim palettes on rebuild in `gaia-core` (trim to the asset-list palette size, or keep the real length in the file); (b) store palettes unpadded in the extracted file; (c) accept an expanded ROM. See §9 decision 2.

## 8b. Pass 2 findings and hazards

- **Capacity closed by decision (2026-11-19):** a larger ROM is accepted, so §8a is no longer a blocker. The rebuild already writes a 2 MiB size byte in the header (`0x0B` at `0x7FD7`) for the 1,081,344-byte output.
- **Hazard R-2 (open): bank-base idioms.** About 60 operands print as `$&meta_tables_008000+N, X/Y` (and a few `binary_048000+N`, `code_010000`, `lookup_080000`, `spc_030000`). They are really `$8000 + field offset` used with an actor-held pointer relative to the bank base (for example `LDY $0038, X` / `LDA $8000, Y`), not references to the table. `meta_tables_008000` is `movable`, and the rebuild already puts it at a different place (`E490` in the first page). - **Known noise:** the rebuild prints about 3,387 "Cross bank call" warnings (3,369 LoROM false positives plus 18 real `COP asciistring_*` cross-bank operands); see the migration plan.
