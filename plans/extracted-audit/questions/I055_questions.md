# I055 open questions (`docs/code/flags-switches-and-inventory-bytes.md`: the shared bit space, event flags, chests, lairs and switches, the permanent map changes, the inventory bytes, the progress items, the souls)

IDs are scoped to this iteration and cover only new findings. Nothing here is written into names, notes, comments, `blocks.json`, `overrides.json` or the docs as fact beyond what the document marks as static reading. Mode: R = static read only, R+S = read, then confirm with a short Mesen2 run, S = needs a runtime run, D = needs a decision. Tag DISCREPANCY marks a mismatch between the ROM text or code and a document (the walkthrough or `docs/`); tag GAP marks a claim the static read cannot settle.

No DISCREPANCY: the game terms of the document (Master's Emblems A-H and the Magic Bell exchange, the six stones, the Red-Hot items and the Phoenix, the five souls, Medical Herb, Strange Bottle, equip-to-give) agree with `items.md`, `sidequests.md`, `02-grass-valley.md`, `03-greenwood.md`, `04-st-elles.md` and chapters 05-08 as far as static reading can check. Spelling differences between the ROM text and the walkthrough (`Goat s Food`, `Red+Hot`, the two `Leaves`, `a pass`) are the known extractor and naming issues of OQ-I027-3, OQ-I004-6 and OQ-I012-12.

Static answers recorded in the document (and in the notes and comments of `edits/I055.json`):

- OQ-I011-13 and OQ-I031-5: flag `$FF` (`$1F07`, bit 7 of `$1A7D`) is set at every start-up by `InitFixedState` and nothing clears it (no `COP 09` names it, `ClearBitInArray` has no caller, the per-scene clear is byte 0 of `event_flags`), so the 13 `FlagMapPatchTable` rows that test it always apply. Runtime half: OQ-I055-5.
- OQ-I035-7: flag `$1B01` is the Green Stone's given flag; flags `$1B00-$1B05` pair with the stones `$3A-$3F`, and the six path markers of `gv_up_above_actors_and_name_entry` read them (six `COP 08` and six `COP 07`).
- OQ-I037-4 and OQ-I035-6 (the "no reader found" part): `$0706`, `$0A00` and `$0907` (and `$0502`, `$0601`) are bit numbers of `FlagMapPatchTable` rows, so `ApplyFlagMapPatches` reads them at scene load. What each patch draws is not checked at runtime.
- The one reader of `switch_owner_table` is `FacePlayerTowardReturnTarget`; the table is zeroed only on a return trip, not at every scene load (the note of `RegisterSwitchOwner` said the opposite and "readers not traced yet").
- The chest array `$1A7E` is bit numbers `$100-$17F` of the same bit space as the event flags (the note of `data_chest_lists` called it part of the switch array).
