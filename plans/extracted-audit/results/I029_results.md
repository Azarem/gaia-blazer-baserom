## Findings and corrections

- **FM-A7 corrections** (the code disagrees, the notes follow the code):
  - The parallax ratio word is read with the high nibble as numerator and the low nibble as divisor (checked against `lib_map_streaming`); the notes use that order.
  - `ApplySceneProfile` clobbers X and restores Y; the part note's Clobbers line says so.
  - The raw tileset and raw tilemap copies depend on `dp$2E` being `$7E` (`OQ-I011-1`); the notes say so instead of treating the destination bank as fixed.
  - The boot clear (`InitHardwareAndClearWram`) needs DBR `$00`-compatible addressing of the registers; its note records the DBR requirement.
  - Caller and actor names in the FM text (pre-regroup file names) were replaced by the current file and label names; a '19 call sites' figure was a line number, not a count; the glyph cells are ten, not nine.
  - Speculative story claims about the dream rooms and the variant rows were left out of the notes; `OQ-I011-5` and `-6` keep them as questions.
- **Scene load model.** An asset record is `area, scene, commands..., 00`; each command byte has one bit set and the loader tries the bits from `$80` down to `$01` (graphics, palette, tileset, tilemap, `asset8` (profile, jump, label), `meta4`, music, spritemap). Asset pointers are linear file offsets turned into SNES addresses by `ReadAssetPointer`; ten 3-byte cells at `$0407`-`$0424` cache the last pointers so an unchanged asset is not decoded again; `asset_skip_mask` bits 0-5 switch one command kind off. The block note of `lib_scene_asset_loader` tabulates this.
- **`scene_variant` is a one-shot music-record selector.** `LoadSceneMusic` plays a music record only when its variant byte equals `scene_variant`; `code_0279B5` clears it after the load; `LookupSceneVariant` or profile byte 11 bits 6-7 set it. Meaning of the six variant-0 rows: `OQ-I011-5`, `-6`.
- **Pause banner.** `pause_latch` is a held-Start latch (set on press, cleared once Start is released), not a counter of the banner time; the banner prints the location name by `[TBL:&LocationNameList,1C6A]` and the lair counter unless `no_combat_scene` is set or A is held. The walkthrough confirms the lair count ('the number of Monster Lairs in the area can be found by pressing the Start Button').
- **`OQ-I028-2` is answered.** `SaveSlotLineTemplates` is typed Binary in the extract, which is why the `[02:3` search found no user; its bytes `01 D4 02 02 03` are `[CUR:2D4][02:3]`, the slot name at `$0447`.
- **Walkthrough check.** The location, boss and screen names of the name list and the banner agree with the walkthrough; no DISCREPANCY arose. The intro and ending narration is not quoted in the walkthrough, so its wording rests on the ROM text.
- **Scope decisions.** Five routines of `lib_scene_map_patches` (`code_0112F5`, `code_011395`, `code_011445`, `code_0114D0`, `code_0114E4`) belong to no function-map row; they stay unannotated (`OQ-I029-1`). The staff roll string `asciistring_016264` in `gv_epilogue_texts` belongs to the front-end batch (`OQ-I029-5`).
- **Hex to decimal.** The hex file offsets of the data parts were converted to decimal with the shell `printf` calculator (the only shell calculation); there was no ad-hoc script for names, notes, comments or docs. The count of profiles with byte 11 bit 5 and byte 4 bit 7 in the questions was read from the extracted records with `rg` and `awk` (read-only).
- **Ad-hoc scripts:** none were written. The only hand edits are `us/mnemonics.json` and `docs/wram-memory-map.md`, for which no tool exists, and the checklist and record files.
